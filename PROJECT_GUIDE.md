## Data decisions

* **Official splits only.** Train 350, dev 50, test 100 documents. Model selection uses dev;
  test is evaluated once with the best dev checkpoint.
* **Sentence-level units.** All SciERC relations are intra-sentence, so sentences are the
  unit of NER and RE. Neighbouring sentences can be added as encoder context
  (`context_window`), which does not change the label space.
* **No redistribution.** The release has no stated licence; data is downloaded by script.

## NER: span classification

A BIO tagger assigns one label per token and therefore cannot represent the nested
entities present in SciERC (61 nested pairs in train, 20 in test). The model instead
enumerates all spans of up to `max_span_length = 8` tokens (99.3 % coverage) and classifies
each one independently into the six types or `O`:

```
h = SciBERT(sentence [+ context])               # sub-word states
span(i, j) = [h_first_subword(i); h_last_subword(j); width_embedding(j - i + 1)]
logits = MLP(span)                              # 2 hidden layers of 150 units, ReLU, dropout
loss = cross-entropy over all enumerated spans
```

Decoding keeps every span whose arg-max label is not `O` (`allow_overlap: true`), so nested
predictions are possible. The alternative greedy non-overlapping decoder is available for
comparison. Two learning rates are used: a small one for the pretrained encoder and a
larger one for the randomly initialised span head.

Sub-tokens: each word is split by the WordPiece tokenizer; a span uses the first sub-token
of its first word and the last sub-token of its last word. Labels are never assigned to
individual sub-tokens, so there is no label-alignment step to get wrong.

## Relation extraction: typed entity markers

For each ordered pair of distinct entities in a sentence, markers are inserted around both
arguments, for example `<S:Method> ... </S:Method>` and `<O:Task> ... </O:Task>`. The
24 marker tokens are added to the tokenizer and their embeddings learned. The relation
representation is the concatenation of the encoder states at the two opening markers,
followed by layer normalisation and a linear layer over eight classes (seven relations plus
`NO-RELATION`). This follows Zhong and Chen (2021).

* **Direction.** (A, B) and (B, A) are separate instances; the marker roles carry direction.
* **Symmetric relations.** COMPARE and CONJUNCTION are annotated once. In training, both
  directions are positives. At inference both directional scores are merged and the
  relation is emitted once with the earlier span as head. The metric matches symmetric
  relations irrespective of order.
* **Negatives.** 81 % of candidate pairs carry no relation. The GPU configuration uses all
  pairs; the CPU configuration samples 1.5 negatives per positive, redrawn every epoch, and
  still scores every pair at evaluation.
* **Type constraints.** Entity types are given to the classifier through the markers rather
  than hard-coded rules; the type signatures of predicted triples are audited in
  Experiment 4 against those observed in training.

Experiment A builds candidate pairs from gold entities; Experiment B from predicted entities
(the NER predictions saved by `train_ner`). A relation counts as correct under the
*boundaries* criterion when both argument spans and the label are correct, and under the
*strict* criterion when the argument types are also correct.

## Training procedure and resumption

`CheckpointManager` writes `checkpoints/last.pt` atomically (temporary file then rename)
with model, optimiser, scheduler, AMP scaler, epoch, global step, best dev score and RNG
states. Re-running the same command resumes from it, including inside an epoch (batches
already seen in the interrupted epoch are skipped in the same shuffled order). The best dev
checkpoint is exported separately to `best/` with its tokenizer and configuration.
Gradient accumulation and mixed precision (CUDA only) are supported.

Training logs are JSON lines (`train_log.jsonl`). MLflow was not added: runs are few, logs
and metrics are plain files under version control, and an extra tracking server would not
change any result.

### Compute actually used

No GPU is available on the development machine and remote GPU use (Kaggle) was declined,
so the reported models were trained on CPU (8 cores, 16 GB RAM) with
`configs/ner_cpu.yaml` and `configs/re_cpu.yaml`. Compared with the GPU configurations,
these use no cross-sentence context, fewer epochs and negative sampling for RE. The GPU
configurations are provided and used by the notebooks when CUDA is present, but they have
not been run; no result in this repository comes from them.

Measured wall-clock training time: 1 h 54 min for NER (10 epochs) and 6 h 15 min for RE
(5 epochs, slowed by memory pressure). Checkpoints are about 1.3 GB because they include
the AdamW state; exported `best/` models are about 420 MB each.

### Decoding

NER decoding is a setting (`configs/graph.yaml`, `extraction.ner_decoding`). The reported
results use `nested`, fixed before evaluation. The ablation in
`reports/metrics/ner_decoding.json` shows that non-overlapping decoding is 0.32 F1 higher
on dev; with a single run this difference is not conclusive.

## Knowledge graph construction

### Entity resolution rules

1. Mentions are merged into one entity only with identical type and identical normalised
   key. Normalisation: Unicode NFKC, lower case, hyphen spacing, leading determiners
   removed, last word singularised, trailing acronym definition removed when it matches.
2. An acronym defined in a document resolves to its long form within that document.
3. `Generic` mentions are never merged (no coreference resolution); bare head nouns such
   as "method" or "model" are merged only within their document.
4. Pairs of entities of the same type with token Jaccard similarity of at least 0.75 are
   reported as candidate duplicates, not merged.

The consequence is that identical strings with different types ("parsing" as Task and as
Method) remain separate nodes, which the specification requires.

### Neo4j schema

```
(:Document {id, title, source, extractor, model_version})
  -[:HAS_MENTION]->(:Mention {id, text, type, sent_index, start, end, char_start, char_end,
                              page, score})
  -[:REFERS_TO]->(:Entity {id, name, type, key, scope, aliases, status, max_score})
(:Entity)-[:USED_FOR|FEATURE_OF|HYPONYM_OF|PART_OF|COMPARE|CONJUNCTION|EVALUATE_FOR
           {id, score, support, evidence_docs, evidence_sentences, status, source,
            model_version, verified_by, verified_at, review_note}]->(:Entity)
(:Entity)-[:INFERRED {id, relation, rule, premises, basis, score, status: 'inferred'}]->(:Entity)
```

Uniqueness constraints on `Entity.id`, `Document.id`, `Mention.id`; range indexes on
`Entity.key`, `Entity.type`, `Entity.status`; a full-text index on entity name and key.
Ingestion uses `UNWIND` batches (default 500 rows) in managed write transactions and is
idempotent (identifiers are hashes of content).

### Knowledge layers

| Layer | Where | Meaning |
|---|---|---|
| predicted | relation `status = 'predicted'` | model output with evidence sentences |
| verified | relation `status = 'verified'` | gold annotation or human review |
| inferred | `:INFERRED` edges | derived by a named rule from verified premises |
| hypothesis | computed on demand | unlinked pairs ranked by shared neighbours |

A prediction never downgrades a verified edge. All exploration queries filter on
`status IN ['predicted', 'verified']` and restrict traversals to the seven relation types,
so inferred edges and provenance edges never appear in paths. A multi-hop path is shown as
an indirect association, not as a scientific relation between its endpoints.

### Query safety

Clients choose a query by name; parameters are validated for type, range, length and
allowed values before execution. Cypher cannot parameterise relationship types or
variable-length bounds, so those come from fixed whitelists or validated integers.
Full-text search input is Lucene-escaped.

## Property graph, RDF graph, ontology

* The **property graph** in Neo4j is the operational store: relationships carry properties
  (scores, evidence, status) directly, and traversals are efficient.
* The **RDF graph** is an export for interoperability. RDF triples cannot carry
  properties, so each extracted fact is written both as a direct triple
  (`sgr:entity/x sg:usedFor sgr:entity/y`) and as a reified `sg:Assertion` with confidence,
  status and `prov:wasDerivedFrom` document links.
* The **ontology** (`src/scigraph/resources/scigraph.ttl`) defines classes for the six
  entity types, object properties for the seven relations (COMPARE and CONJUNCTION are
  `owl:SymmetricProperty`), and disjointness between Task, Method, Metric and Material.
  Domains and ranges are kept at `sg:ScientificEntity` because the annotation guideline
  does not restrict argument types strictly.
* **SHACL shapes** check structure (exactly one subject, predicate and object per assertion,
  confidence in [0, 1], allowed status values, provenance present) and warn on EVALUATE-FOR
  assertions whose subject is neither Metric nor Material.

## Procedures

* Regenerate notebooks after changing their sources: `python scripts/build_notebooks.py`.
* Neo4j integration tests and the query/benchmark experiments wipe the database; run them
  only against a disposable instance (`SCIGRAPH_NEO4J_TESTS=1`, `--reset`, `--neo4j`).
* After training, `python scripts/make_report.py` refreshes `reports/` from the run outputs.
* Model weights are not committed (`/models`, `/outputs` are git-ignored). Copy
  `outputs/ner/best` and `outputs/re/best` to `models/ner` and `models/re` for the API.
